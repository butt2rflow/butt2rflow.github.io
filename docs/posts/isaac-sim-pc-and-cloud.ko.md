# 로봇의 뇌를 엣지에 올리기 — Isaac Sim편: RTX 3090 PC와 클라우드 GPU에 가상 작업 셀 만들기

> **현장 노트 · Isaac Sim편.** [시뮬레이터편](jetson-ursim-planners.md)의 URSim은 **로봇 컨트롤러**를 흉내 냅니다. 드라이버와 보호 정지는 진짜처럼 동작하지만 물리도, 물체도, 카메라도 없어요. 그 글 끝에 "반짝이는 부품에서 깊이가 비는지, 집은 부품이 미끄러지는지는 Isaac Sim의 몫"이라고 적었습니다. 이번에는 그 Isaac Sim을 놀고 있던 RTX 3090 PC와 클라우드 GPU에 직접 올려 봤어요.

결론부터 말하면, 3090 PC로 충분했습니다. 클라우드 GPU는 더 빠르지 않았고, 대신 PC를 비워 두고 여러 대를 동시에 돌릴 수 있다는 점이 쓸모였어요. 이 글은 그 과정에서 잰 숫자와 걸린 함정을 정리합니다.

*(이번 글은 엣지 컴퓨터(Jetson) 없이 PC와 클라우드에서만 한 R&D 기록입니다. 로봇은 모두 **Isaac Sim 안의 UR20 모델**이고, 실제 로봇은 움직이지 않았습니다.)*

## 30초 요약

- **URSim과 Isaac Sim은 합치지 않고 할 일을 나눈다.** URSim은 컨트롤러 경로, Isaac Sim은 물리·카메라·합성 데이터, 둘 다 필요한 확인은 실제 로봇에서.
- **최소 사양 아래인 RTX 3090으로 충분했다.** UR20, 상자 40개, 가상 스테레오 카메라를 실제 카메라 해상도로 계산해 초당 19프레임, GPU 메모리는 24 GB 중 5 GB 미만.
- **'약한 모터'는 시험 잘못이었다.** 관절을 모두 0으로 둔 자세를 중심으로 흔들자 팔이 바닥을 눌렀다. 준비 자세에서 시작하자 오차는 약 0.01 rad. 모델의 질량·토크·속도 한계는 실제 UR20과 같았다.
- **가상 카메라와 가상 팔을 ROS 2 토픽으로 내보냈다.** 엣지 컴퓨터가 보기에는 진짜 카메라, 진짜 로봇과 같은 모양이다. 윈도판 기본값(Jazzy, Zenoh)을 Humble과 Fast DDS로 바꾸고 UDP 버퍼를 16 MB로 키워야 했다.
- **합성 데이터 500장을 한 장에 0.79초로 만들었다.** 다만 NVIDIA 예제를 따라 촬영마다 렌더를 껐다 켜자 GPU 메모리가 한 장에 약 130 MB씩 새서 170~190장에서 멈췄다. 껐다 켜기를 빼니 메모리가 평평해졌다.
- **클라우드 L4는 3090보다 빠르지 않았다.** 같은 시험에서 3090 속도의 절반에서 5분의 4 정도, 병목은 GPU가 아니라 CPU였다. 클라우드의 쓸모는 속도가 아니라 동시 실행과 PC 비워 두기다. 검증 전체 비용은 약 1.45달러.

## 왜 Isaac Sim인가: URSim과 할 일 나누기

![시뮬레이터 둘, 실제 로봇 하나: 무엇을 어디서 확인하나](../assets/diagrams/r9-split.svg)

처음에는 둘을 합치려고 했습니다. URSim이 계산한 관절 각도를 Isaac Sim 속 로봇에 그대로 비추면, 진짜 컨트롤러와 진짜 같은 화면을 한 번에 얻을 것 같았거든요. 그런데 그렇게 하면 Isaac Sim 쪽 로봇은 각도를 받아 따라 그리기만 하는 **유령**이 됩니다. 물리가 꺼져서 상자를 뚫고 지나가고, URSim은 무엇에 부딪혔는지 알 길이 없어요.

그래서 할 일을 나눴습니다. Isaac Sim은 자기 안의 UR20 모델을 물리로 움직이며 **주변 세계**(중력, 접촉, 카메라 영상과 깊이)를 맡고, URSim은 엣지 컴퓨터와 함께 **컨트롤러 경로**(드라이버, 보호 정지, 속도 한계)를 맡아요. 둘 다 필요한 확인, 그러니까 진짜 컨트롤러가 진짜 물체를 만지는 순간은 [실물편](jetson-real-robot-first-move.md)처럼 실제 로봇에서 합니다.

Isaac Sim으로 하려는 일은 넷입니다. 학습용 **합성 데이터** 만들기, 큰 GPU에서 깊이 모델을 원래 해상도로 실행해 엣지 컴퓨터에서 해상도를 줄인 값이 얼마인지 재기, 경로 계획을 실제 로봇 전에 확인하기, 그리고 가상 카메라 영상을 엣지 컴퓨터에 넣어 보는 **소프트웨어 인 더 루프(SIL)**예요. 이 글은 그 바탕을 까는 이야기입니다.

## 최소 사양 아래인 3090으로 괜찮을까

Isaac Sim 6.1의 공식 요구 사양은 GPU 최소가 GeForce RTX 4080, 메모리 16 GB 이상, RAM 32 GB 이상(권장 64 GB)입니다. 이 PC는 RTX 3090 24 GB에 RAM 32 GB라 GPU가 최소 등급 아래예요. 새 디스크나 메모리를 사기 전에 윈도에 먼저 설치해서 실제로 재 봤습니다.

시험 장면은 실제로 쓸 작업 셀을 흉내 냈습니다. UR20 모델이 여섯 관절을 사인파로 움직이고, 상자 40개를 바닥에 떨어뜨려 더미를 만들고, 실제 카메라(OAK-D)와 같은 75 mm 간격의 가상 스테레오 카메라 두 대와 컬러 카메라 하나를 둡니다. 매 프레임 세 카메라의 영상과 깊이를 CPU로 가져와요. ROS 2로 내보낼 때와 같은 복사입니다. 물리는 60 Hz, 화면 없이(headless) 600프레임을 쟀습니다.

| 카메라 설정 | 초당 프레임 | GPU 메모리 최대 |
|---|---|---|
| 카메라 없음 (물리만) | 62.5 | 3.1 GB |
| 스테레오 480×288 (Jetson에서 깊이 모델을 실행하는 해상도) | 30.6 | 3.5 GB |
| 스테레오 640×400 + 컬러 720p | 27.1 | 3.6 GB |
| 스테레오 1280×800 + 컬러 1080p (실제 카메라 최대) | 18.9 | 4.3 GB |

가장 무거운 설정에서도 초당 19프레임, GPU 메모리는 24 GB 중 5 GB가 안 됐습니다. 최소 사양 아래라는 걱정은 이 작업에서는 문제가 되지 않았어요. 실제로 쓸 때는 카메라를 매 물리 단계마다 찍을 필요가 없습니다. Jetson의 깊이 모델은 초당 30번보다 훨씬 느리게 동작하니까요. 아래 SIL에서는 물리 60 Hz, 카메라 30 Hz로 나눠서 실제 시간의 0.93배까지 올렸습니다.

## 약한 모터가 아니라 바닥이었다

![약한 모터가 아니라 바닥이었다](../assets/diagrams/r9-floor.svg)

첫 측정에서 이상한 숫자가 나왔습니다. 관절이 명령을 잘 따라가지 못했어요. 어깨 관절은 0.126 rad, 손목 하나는 0.615 rad(약 35°)나 어긋났고, 관절마다 0.3 rad씩 움직이라는 시험에서 어깨와 팔꿈치는 꿈쩍도 하지 않았습니다. Isaac Sim의 UR20 모델은 모터가 약하게 설정돼 있나 싶었죠.

모델을 하나씩 확인해 보니 모터는 멀쩡했습니다. 링크 질량은 UR이 공개한 값과 정확히 같았고, 관절 토크 한계(어깨 730 Nm 대 실제 738 Nm)와 속도 한계(어깨 120 °/s)도 실제 UR20과 거의 같았어요. 문제는 시작 자세였습니다. 관절을 모두 0으로 두면 UR20의 팔은 어깨 높이에서 **수평으로** 뻗고, 어깨와 팔꿈치를 + 방향으로 돌리면 팔이 **아래로** 내려갑니다. 사인파 시험은 바로 이 자세를 중심으로 흔들었으니 팔을 바닥과 상자 더미 속으로 누른 셈이에요. 중력을 버티는 데는 어깨에 328 Nm면 되는데 모터는 700 Nm 넘게 밀고 있었습니다. 바닥에 막혀서요.

팔을 든 준비 자세를 중심으로 흔들자 모든 관절의 오차가 0.006~0.014 rad, 60 Hz 한 칸 정도의 지연으로 줄었습니다. 같은 0.3 rad 단계도 약 0.5초 만에 오차 없이 끝났어요. [시뮬레이터편](jetson-ursim-planners.md)의 "바닥은 모든 요청에"와 같은 교훈입니다. 시뮬레이터에서 숫자가 이상하면 모델보다 **시작 자세가 바닥에서 떨어져 있는지**부터 봐야 합니다.

같은 날 걸린 작은 함정이 하나 더 있습니다. Isaac Sim의 관절 각도 읽기 함수가 돌려주는 배열은 복사본이 아니라 **시뮬레이터 버퍼를 그대로 비추는 창**이에요. '시작 자세'로 저장해 둔 값이 움직임이 끝나면 '끝 자세'와 같아져 있었습니다. 기억해 둘 값은 `.copy()`로 따로 떠 둬야 합니다.

## 가상 카메라와 가상 팔을 ROS 2 토픽으로

![가상 카메라와 가상 팔을 ROS 2 토픽으로](../assets/diagrams/r9-sil.svg)

다음은 SIL의 PC 쪽입니다. 목표는 엣지 컴퓨터가 지금 실제 카메라와 실제 로봇에서 받는 것과 **같은 모양의 데이터**를 Isaac Sim이 내보내는 것이에요. 그러면 엣지 컴퓨터의 깊이 모델과 경로 계획은 코드를 바꾸지 않고 가상 세계를 보게 됩니다. 로봇 쪽은 `topic_based_ros2_control`이 관절 상태와 명령 토픽을 일반 ros2_control 하드웨어처럼 보이게 해 주니, cuMotion은 실제 로봇에 보내듯 궤적을 보내면 돼요.

이번에는 엣지 컴퓨터 없이 PC 쪽만 만들고, 따로 띄운 토픽 검사기로 확인했습니다.

| 토픽 | 내용 | 실제 속도 |
|---|---|---|
| `/clock` | 시뮬레이션 시계 | 약 56 Hz (실제 시간의 0.93배) |
| `/isaac_joint_states` | 관절 상태 | 약 56 Hz |
| `/isaac_joint_commands` | 관절 명령 (받기) | +0.300 rad 명령이 그대로 도착, 다른 관절 흔들림 없음 |
| `/oak/left`, `/oak/right` | 스테레오 흑백 640×400 | 약 28 Hz |
| `/oak/rgb` | 컬러 1280×720 | 약 28 Hz |
| 카메라 정보 세 개 | 렌즈 값, 오른쪽 카메라에서 75.0 mm 기준선 | 약 28 Hz |

스테레오 네 토픽(왼쪽·오른쪽 영상과 각각의 카메라 정보)은 224장 모두 같은 시각 도장을 받았습니다. 깊이 모델은 왼쪽과 오른쪽이 같은 순간에 찍혔다고 믿고 계산하니, 이게 어긋나면 깊이가 틀어져요.

여기까지 오면서 걸린 것들입니다.

- **윈도판 Isaac Sim 6.1의 ROS 2 기본값은 Jazzy와 Zenoh.** 엣지 컴퓨터는 Humble에 Fast DDS라서 그대로는 서로 보이지 않습니다. 내장 Humble과 `rmw_fastrtps_cpp`를 직접 지정했어요. 내장 설정 스크립트는 `ROS_DISTRO`가 비어 있을 때만 라이브러리 경로를 넣는다는 점도 주의할 곳입니다.
- **사진 한 장이 2.7 MB.** 컬러 1280×720 한 장이 2.7 MB인데, Fast DDS 기본 버퍼로는 '최선 노력' 구독자가 약 75%를 잃었습니다. 보내고 받는 UDP 버퍼를 16 MB로 키운 설정 파일을 썼어요. 리눅스는 `net.core.rmem_max`가 이보다 작게 막혀 있어서, 엣지 컴퓨터 쪽도 이 값을 함께 올려야 합니다. 클라우드 리눅스에서 이 값을 그대로 두자 컬러 영상이 5.7 Hz밖에 오지 않았어요.
- **스테레오 흑백은 직접 만들어 보냄.** Isaac Sim의 카메라 도우미는 컬러만 내보냅니다. 실제 카메라의 스테레오는 흑백이라, 컬러 영상을 밝기로 바꿔 Python에서 흑백으로 보냈어요.
- **관절 상태 노드는 로봇의 뿌리 관절을 가리켜야.** 로봇 전체를 가리키면 "일치하는 관절 묶음이 없다"는 경고만 매 프레임 남기고 아무것도 보내지 않습니다.

엣지 컴퓨터 쪽(시뮬레이션 시계 쓰기, 토픽 이름 맞추기, 직결 이더넷)은 다음 단계예요. 영상이 초당 50~80 MB라 이 연결은 같은 랜에서 해야 하고, 인터넷 너머 클라우드와는 하지 않습니다.

## 합성 데이터: 한 장에 0.79초

![같은 순간을 네 가지로 본 합성 데이터 한 장. 왼쪽 위 컬러 영상, 오른쪽 위 깊이(밝을수록 가까움), 왼쪽 아래 종류별 색칠(바닥·로봇·상자), 오른쪽 아래 2D 상자 표시(노랑은 상자, 초록은 로봇)](../assets/demos/isaac-sdg-quad.jpg)

*한 번 찍을 때 나오는 네 가지입니다. 컬러 영상, 깊이(밝을수록 가까움), 종류별 색칠, 2D 상자 표시. 상자 표시는 출력 데이터로 이 글에서 그려 넣었어요.*

[로봇은 왜 '가짜 세계'에서 먼저 배우나](robot-simulation.md)에서 다룬 **도메인 랜덤화**를 실제로 해 봤습니다. 한 번 찍을 때마다 상자를 다시 떨어뜨리고, 상자 색, UR20의 자세, 조명 밝기, 카메라 위치를 조금씩 바꿔요. 그리고 물리가 가라앉기를 기다린 뒤 한 장을 렌더합니다. 한 장에 컬러 영상, 깊이, 종류별 색칠(상자·로봇·바닥), 2D 상자 표시가 함께 나옵니다. 사람이 상자 30개에 일일이 테두리를 그릴 필요가 없다는 게 합성 데이터의 핵심이에요.

RTX 3090에서 500장에 한 장당 0.79초, 약 6분 30초가 걸렸습니다. 다만 여기까지 오는 길에 메모리 누수가 하나 있었어요.

## 촬영마다 130 MB씩 새던 메모리

![합성 데이터 스크립트의 GPU 메모리](../assets/diagrams/r9-leak.svg)

처음 만든 스크립트는 클라우드에서 97장, 드라이버를 바꾼 뒤에는 169장에서 멈췄습니다. GPU 오류(Xid 31)가 나고 렌더러가 응답하지 않았어요. 처음에는 클라우드 드라이버를 의심했는데, 같은 스크립트를 3090에서 500장 돌리자 188장에서 **GPU 메모리 부족**으로 멈췄습니다. 드라이버가 아니라 스크립트 문제였던 거죠.

원인을 찾으려고 의심 가는 부분을 하나씩 빼고 60장씩 비교했습니다. 색 바꾸기를 빼도, 물리 기다리기를 빼도 메모리는 60장에 2.2 GB에서 9.9 GB로 똑같이 늘었어요. 한 장에 약 130 MB입니다. 그런데 **렌더 갱신을 껐다 켜는 줄**을 빼자 메모리가 약 3 GB에서 멈췄습니다.

이 줄은 NVIDIA의 합성 데이터 예제가 쓰는 방식이에요. 물리를 가라앉히는 동안은 렌더하지 않도록 매번 렌더 갱신을 끄고, 찍을 때만 켭니다. Isaac Sim 6.1에서는 이걸 매번 반복하면 GPU 메모리가 조금씩 새고, 24 GB를 170~190장에서 다 씁니다. 빼고 나서도 손해가 없었어요. 이 스크립트는 물리를 기다리는 동안 원래 렌더를 하지 않는 방식으로 진행해서, 껐다 켤 이유가 처음부터 없었습니다. 고친 뒤에는 3090에서도 클라우드에서도 500장을 모두 마쳤고, 메모리는 평평했어요(3090 약 3.0 GB, L4 약 2.4 GB). 스크립트는 이제 10장마다 GPU 메모리를 기록합니다.

교훈은 **장시간 시험을 해 봐야 보이는 문제가 있다**는 것입니다. 10장짜리 첫 시험은 멀쩡했어요. 합성 데이터는 수만 장을 만들 일이니, 몇백 장짜리 시험에서 메모리 기록을 함께 남기는 편이 좋습니다.

## 클라우드 GPU: 더 빠르지 않았다

3090 PC는 한 대뿐이고, 합성 데이터를 만드는 동안은 다른 일을 하기 어렵습니다. 그래서 같은 작업을 클라우드 GPU에서도 해 봤어요.

먼저 고를 수 있는 GPU가 정해져 있습니다. Isaac Sim은 렌더링에 **RT 코어**를 쓰기 때문에, AI 학습용으로 유명한 A100이나 H100은 지원하지 않아요(공식 요구 사양 문서에 명시). L4, L40S, A10G처럼 그래픽 기능이 있는 GPU를 골라야 합니다. 2026년 10월 4일에 확인한 가격으로는 구글 클라우드의 L4 스팟 인스턴스(`g2-standard-8`)가 시간당 약 0.51달러로 가장 쌌습니다. 스팟은 클라우드가 남는 자원을 싸게 빌려주는 대신 언제든 회수할 수 있는 방식이에요. Isaac Sim은 NVIDIA가 공개한 Docker 이미지로 실행했습니다.

![RTX 3090 PC vs 클라우드 L4: 초당 프레임](../assets/diagrams/r9-fps.svg)

같은 시험 장면에서 L4는 3090 속도의 49~83%였습니다. 눈여겨볼 점은 L4가 카메라 해상도와 상관없이 초당 16~20프레임 근처에서 멈춘다는 거예요. 해상도를 올려도 느려지지 않는다는 건 GPU가 일을 다 못 해서가 아니라, **CPU(2.2 GHz 가상 코어 8개)가 병목**이라는 뜻입니다. 3090 PC의 CPU가 한 코어당 더 빨랐던 거죠. 합성 데이터도 한 장에 0.91초로 3090(0.79초)보다 조금 느렸어요. 관절 추종 오차는 소수점 셋째 자리까지 같아서, 물리 계산은 어디서 돌려도 같았습니다.

그래서 클라우드의 쓸모는 속도가 아닙니다. **여러 대를 동시에** 돌려 합성 데이터를 나눠 만들거나, 3090 PC를 다른 일에 비워 둘 때 씁니다. 더 빠른 한 대가 필요하다면 L40S급으로 올라가야 해요.

| 항목 | 비용 |
|---|---|
| L4 스팟 인스턴스 약 2.5시간 | 약 1.30달러 |
| 디스크 150 GB, 2.5시간 | 약 0.05달러 |
| 데이터 내려받기 (1 GB 미만) | 약 0.10달러 |
| **합계** | **약 1.45달러 (약 2캐나다달러)** |

검증이 끝나면 인스턴스와 디스크를 모두 지워서, 이후 비용은 0입니다. 예산 경보만 남겨 뒀어요.

### 클라우드에서 걸린 것들

클라우드 이미지를 그대로 쓰면 Isaac Sim이 바로 동작하지 않았습니다. 세 군데를 손봤어요.

- **카메라가 빈 화면.** 구글 클라우드의 GPU 이미지는 AI 계산용 드라이버만 들어 있어서 그래픽 라이브러리(Vulkan)가 없습니다. 드라이버와 같은 버전의 그래픽 라이브러리를 따로 설치해야 해요.
- **설치했는데도 컨테이너 안에서 안 보임.** Docker의 흔한 GPU 옵션(`--gpus all`)은 계산용 라이브러리만 넘깁니다. NVIDIA 런타임을 등록하고 `--runtime=nvidia`와 모든 드라이버 기능(`NVIDIA_DRIVER_CAPABILITIES=all`)을 함께 줘야 그래픽까지 넘어갑니다.
- **원격 화면 서버가 안 뜸.** 화면을 영상으로 보내는 기능은 GPU의 영상 인코더 라이브러리가 필요한데, 이것도 이미지에 없었어요.

드라이버는 이미지에 들어 있던 580대 버전에서도 동작했지만, Isaac Sim 6.1의 요구 사양(리눅스 595.58.03 이상)에 맞춰 595대로 올렸습니다. 새 드라이버에서 처음 렌더할 때는 셰이더를 약 10분 동안 컴파일하니, 컴파일된 캐시를 저장해 두면 다음부터 시작이 빨라져요.

![클라우드 L4에서 실행 중인 Isaac Sim 화면을 로컬 PC의 스트리밍 클라이언트로 본 모습. 가운데에 UR20 모델과 상자 더미, 오른쪽에 장면 구성 목록](../assets/demos/isaac-cloud-stream.jpg)

*클라우드의 Isaac Sim을 로컬 PC에서 본 화면입니다. NVIDIA의 WebRTC 스트리밍 클라이언트로 연결했고, 팔이 움직이는 모습이 실시간으로 보였어요. 그림 속 글자는 원래 화면 그대로입니다.*

화면 없는 클라우드 서버에서도 Isaac Sim 화면 전체를 영상으로 받아 볼 수 있습니다. 스트리밍 포트를 인터넷에 열어 두는 대신, 서버에 WireGuard를 직접 설치해 로컬 PC와 둘만 쓰는 터널을 만들고 그 안으로 연결했어요. 한 가지 함정은 스트리밍 서버에 **클라이언트가 접속할 주소**를 알려 줘야 한다는 점입니다. 주소가 다르면 연결은 되는데 화면이 까맣게 나올 수 있어요.

## 정리

| 확인한 것 | 결과 | 걸린 것 |
|---|---|---|
| 역할 나누기 | 세계는 Isaac Sim, 컨트롤러는 URSim, 둘 다는 실제 로봇 | URSim을 비추면 Isaac 로봇은 유령이 됨 |
| RTX 3090 PC (최소 사양 아래) | 실제 카메라 해상도로 초당 19프레임, 5 GB 미만 | RAM 32 GB는 빠듯함 |
| UR20 모델 | 질량·토크·속도 한계가 실제와 같음, 오차 약 0.01 rad | 관절 0 자세는 팔이 바닥을 누름 |
| ROS 2 토픽 | 카메라 약 28 Hz, 관절 약 56 Hz, 실제 시간의 0.93배 | Jazzy·Zenoh 기본값, 2.7 MB 영상에 16 MB 버퍼 |
| 합성 데이터 | 500장, 한 장 0.79초 (L4 0.91초) | 렌더 껐다 켜기가 한 장에 130 MB 누수 |
| 클라우드 L4 | 3090의 49~83%, CPU 병목, 약 1.45달러 | 그래픽·인코더 라이브러리, NVIDIA 런타임 |

- **비싼 장비를 사기 전에 가진 것으로 먼저 잰다.** 최소 사양 아래라도 실제 작업에서는 충분할 수 있습니다.
- **숫자가 이상하면 모델보다 시험을 먼저 의심한다.** 이번에는 시작 자세가 바닥 속이었습니다.
- **합성 데이터는 장시간 시험과 메모리 기록을 함께.** 10장짜리 시험에서는 누수가 보이지 않았어요.
- **클라우드는 속도가 아니라 동시 실행용.** 한 대만 놓고 보면 3090 PC가 더 빨랐습니다.
- **엣지 컴퓨터와의 연결은 같은 랜에서.** 영상이 초당 수십 MB라 인터넷 너머로는 하지 않습니다.

다음은 엣지 컴퓨터 쪽입니다. 실제 카메라의 보정값을 가상 카메라에 넣고, Jetson의 깊이·자세 모델이 Isaac Sim의 영상을 받아 cuMotion으로 가상 UR20을 움직이게 할 계획이에요.

### 용어 설명

- *Isaac Sim*: NVIDIA의 로봇 시뮬레이터. 물리와 사진에 가까운 카메라 영상을 GPU로 계산한다
- *URSim*: UR이 무료로 제공하는 가상 컨트롤러. 진짜 컨트롤러 소프트웨어를 PC에서 실행한다
- *합성 데이터*: 시뮬레이터에서 렌더해 만든 학습용 영상과 정답(깊이, 색칠, 상자 표시)
- *도메인 랜덤화*: 색, 조명, 위치 등을 매번 바꿔 찍어, 모델이 가짜 세계의 특정 모습에 매이지 않게 하는 방법
- *SIL(소프트웨어 인 더 루프)*: 실제 센서와 로봇 대신 시뮬레이터를 연결해 실제 소프트웨어를 그대로 시험하는 방식
- *토픽*: ROS 2에서 데이터가 오가는 이름 붙은 통로
- *Fast DDS · Zenoh*: ROS 2가 쓰는 통신 방식. 양쪽이 같아야 서로 보인다
- *headless*: 화면 창 없이 실행하는 방식
- *RT 코어*: 빛의 경로를 계산하는 GPU 안의 전용 회로. Isaac Sim의 렌더링에 필요하다
- *스팟 인스턴스*: 클라우드가 남는 자원을 싸게 빌려주는 대신 언제든 회수할 수 있는 서버
- *셰이더 캐시*: GPU용으로 미리 컴파일해 둔 렌더링 프로그램. 있으면 시작이 빠르다
- *WireGuard*: 두 컴퓨터 사이에 암호화된 사설 터널을 만드는 VPN 소프트웨어
