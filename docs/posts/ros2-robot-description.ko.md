# 티치 펜던트에서 ROS 2로 (2) — 로봇을 ROS에 설명하기: URDF, TF2, ros2_control, RViz

> **티치 펜던트에서 ROS 2로 · 4부작 중 2부.** [1부](ros2-for-robot-programmers.md)에서 ROS 2가 노드와 메시지로 된 배선이라는 걸 봤습니다. 이번에는 그 배선에 로봇을 연결하는 법입니다. [3부](moveit2-goals-not-points.md)는 MoveIt 2, [4부](isaac-ros-gpu.md)는 Isaac ROS와 cuMotion입니다.

화낙 컨트롤러는 자기가 어떤 로봇에 붙어 있는지 이미 압니다. 팔 길이, 관절 범위, 모터 특성이 공장에서 들어가 있고, 펜던트에서는 UFRAME과 UTOOL만 정해 주면 되죠.

ROS는 사정이 다릅니다. PC에서 동작하는 일반 프로그램이라서, 연결된 로봇이 어떻게 생겼는지 처음에는 아무것도 모릅니다. 그래서 세 가지를 알려 주고, 제대로 알아들었는지 눈으로 확인해야 해요.

![컨트롤러는 로봇을 이미 안다. ROS에는 알려 줘야 한다](../assets/diagrams/r2p2-what-ros-needs.svg)

이 글은 그림의 네 줄을 위에서부터 차례로 봅니다.

---

## 30초 요약

- **URDF**는 로봇의 설계도 파일입니다. 링크(단단한 부분)와 조인트(관절)의 사슬, 관절 범위, 3D 모양이 들어 있어요. 팔은 제조사가 주고, 그리퍼와 카메라는 내가 붙입니다.
- **robot_state_publisher**가 설계도와 실시간 관절 각도를 합쳐 로봇 각 부분의 위치를 계산합니다.
- **TF2**는 좌표계 관리자입니다. UFRAME·UTOOL과 같은 역할인데, 번호로 몇 개를 고르는 대신 좌표계들을 나무 모양으로 연결해 둡니다. 카메라가 본 위치를 로봇 기준으로 바꿔 주는 것도 TF2예요.
- **ros2_control**은 모터 제어를 층으로 나눕니다. 궤적을 따라가는 컨트롤러는 모든 로봇 공통이고, 맨 아래 하드웨어 인터페이스만 로봇마다 다릅니다.
- **RViz**는 이 모든 걸 3D로 보여 주는 화면입니다. 로봇이 움직이기 전에 실수를 잡는 곳이에요.

---

## 로봇의 설계도, URDF

URDF(Unified Robot Description Format)는 로봇을 **링크와 조인트의 사슬**로 적은 텍스트 파일입니다.

![로봇 = 링크와 조인트의 사슬](../assets/diagrams/r2p2-urdf-chain.svg)

오른쪽 코드가 관절 하나입니다. "위팔(upper_arm_link)과 아래팔(forearm_link)을 연결하는 회전 관절이고, 이 축으로 ±180°까지 돈다"는 뜻이에요. 펜던트의 관절 범위 설정과 같은 정보가 파일 안에 들어 있는 셈입니다. 여기에 각 링크의 3D 모양 파일이 연결돼서, 화면에 로봇을 그리고 충돌을 검사하는 데 쓰입니다.

직접 처음부터 쓸 일은 드뭅니다. 로봇 제조사가 모델별 설계도를 패키지로 줍니다. 대부분 **xacro**라는 형식으로 쓰여 있는데, 변수와 조각 파일을 쓸 수 있는 URDF예요. TP의 매크로 같은 거라고 보면 됩니다. 내가 할 일은 거기에 내 장비를 붙이는 거예요.

![제조사 설계도 + 내가 단 것 = 우리 셀](../assets/diagrams/r2p2-urdf-compose.svg)

그리퍼와 카메라를 빠뜨리면 ROS는 팔 끝이 비어 있다고 믿어서, 그리퍼가 지그에 걸리는 경로도 문제없다고 판단합니다. 테이블과 고정 지그도 같은 이유로 넣어 둡니다.

## 설계도에 관절 각도를 더하면

설계도는 "생김새"일 뿐이고, 지금 팔이 어떤 자세인지는 모릅니다. 그건 로봇 드라이버가 계속 보내 주는 관절 각도(`/joint_states`, 1부에서 본 그 토픽)에 있죠. 이 둘을 합치는 노드가 **robot_state_publisher**입니다.

![설계도 + 관절 각도 = 모든 부분의 위치](../assets/diagrams/r2p2-rsp.svg)

결과는 `/tf`라는 토픽으로 나갑니다. 로봇의 모든 링크가 지금 어디에, 어떤 방향으로 있는지가 계속 흘러나오고, RViz도 MoveIt 2도 내가 짠 노드도 그걸 받아 씁니다. 펜던트는 이 계산을 화면에 띄우고 끝나지만, ROS에서는 별도 노드가 계산해서 필요한 모든 노드에 방송합니다.

## UFRAME·UTOOL은 ROS에서 TF2가 맡는다

펜던트에서 P[3]을 가르치면 "UFRAME 1 기준으로, UTOOL 1의 끝이 올 위치"로 저장됩니다. 같은 점이라도 어느 좌표계로 보느냐에 따라 숫자가 달라지니까요. 좌표계 자체가 낯설다면 [좌표계와 변환](frames-transforms.md)에 그림으로 풀어 두었습니다.

ROS에서 이 일을 맡는 라이브러리가 **TF2**입니다.

![같은 개념, 이름과 모양만 다르다](../assets/diagrams/r2p2-uframe-utool.svg)

차이는 모양에 있어요. 펜던트는 UFRAME·UTOOL을 번호로 몇 개 만들어 두고 하나씩 골라 씁니다. TF2는 좌표계를 전부 **나무(TF 트리)**로 연결해 둡니다. 맨 위의 `world` 아래 로봇 베이스(`base_link`)에서 관절을 따라 플랜지(`tool0`)까지 가고, 거기서 그리퍼 끝과 카메라로 가지가 뻗죠. 테이블 좌표계는 베이스에 붙은 또 하나의 가지고요.

- **UTOOL**은 `tool0 → gripper_tip` 가지에 해당합니다. 플랜지에서 그리퍼 끝까지 얼마나 떨어져 있는지예요.
- **UFRAME**은 `base_link → table`처럼 베이스에 붙인 좌표계에 해당합니다.
- **카메라**도 한 가지입니다. 팔에 달린 카메라라면 `tool0` 아래에 붙고, 그 위치는 핸드-아이 캘리브레이션(카메라가 툴 어디에 달렸는지 정밀하게 재는 일)으로 한 번 측정합니다.

나무 전체가 연결돼 있으니, 아무 두 좌표계 사이의 관계든 TF2에 물어볼 수 있습니다. 카메라를 붙이면 이 기능을 가장 많이 쓰게 됩니다.

![TF2: 이 점, 베이스 기준으로는 어디야?](../assets/diagrams/r2p2-tf-lookup.svg)

카메라는 부품 위치를 **카메라 기준**으로 알려 줍니다. 로봇을 거기로 보내려면 **베이스 기준** 위치가 필요하죠. TF2에 "이 점을 base_link 기준으로 바꿔 줘"라고 하면 나무를 따라 계산해 줍니다. 터미널에서 두 좌표계 사이를 직접 확인할 수도 있어요.

```text
$ ros2 run tf2_ros tf2_echo base_link tool0
At time 1790561234.512000000
- Translation: [0.412, -0.133, 0.520]
- Rotation: in Quaternion (xyzw) [1.000, 0.000, 0.000, 0.000]
- Rotation: in RPY (degree) [180.000, 0.000, 0.000]
```

위치는 미터로 나오고, 회전은 두 가지로 나옵니다. 쿼터니언은 방향을 숫자 네 개로 적는 방식으로 프로그램끼리 쓰는 형식이고, 아래의 RPY(degree) 줄이 펜던트의 W·P·R에 해당합니다. 사람은 RPY 줄만 읽으면 돼요.

그림 아래쪽 함정은 팔에 카메라를 단 셀에서 가장 흔한 버그입니다. 사진을 찍은 순간과 계산하는 순간 사이에 팔이 움직였다면, "지금"의 카메라 위치로 계산한 결과는 엉뚱한 곳을 가리켜요. TF2는 시간별 기록을 잠시 갖고 있어서, **사진이 찍힌 시각의 변환**을 달라고 요청할 수 있습니다. 메시지마다 붙어 있는 시각(타임스탬프)을 그대로 넘기면 됩니다.

카메라 좌표계는 보통 둘이에요. 카메라 몸체 방향의 `camera_link`와, 렌즈 밖으로 z축이 뻗는 광학 좌표계(`..._optical_frame`)입니다. 인식 결과가 어느 쪽 기준인지 확인하지 않으면 축이 90°씩 틀어진 답이 나옵니다.

## 로봇마다 다른 층만 갈아 끼우는 ros2_control

**ros2_control**은 모터 제어를 층으로 나눕니다.

![맨 아래 한 층만 로봇마다 다르다](../assets/diagrams/r2p2-ros2-control.svg)

- **컨트롤러**는 궤적을 받아 따라가는 부분입니다. 가장 많이 쓰는 `joint_trajectory_controller`는 어떤 로봇이든 같은 코드예요(UR과 화낙 드라이버는 펜던트 속도 슬라이더를 따르는 `scaled_joint_trajectory_controller`를 기본으로 씁니다). 1부에서 본 "궤적을 따라가라" 액션을 받는 게 바로 이 컨트롤러입니다. 여기서 말하는 컨트롤러는 ROS 안의 소프트웨어 부품이고, 로봇 옆의 로봇 컨트롤러(캐비닛)와는 다릅니다.
- **하드웨어 인터페이스**는 그 명령을 이 로봇의 말로 바꿉니다. 로봇마다 다른 건 여기뿐이에요. 흔히 'ROS 2 드라이버'라고 부르는 게 바로 이 층입니다.

UR의 경우 하드웨어 인터페이스가 UR의 RTDE라는 실시간 데이터 통로로 상태를 읽고, 컨트롤러에서 실행 중인 External Control 프로그램에 2밀리초마다(e-Series 기준, CB3는 8밀리초) 목표 위치를 보냅니다. 1부에서 타이밍이 중요하다고 한 그 명령 루프가 여기입니다. 화낙은 공식 ROS 2 드라이버(`fanuc_driver`)를 공개했고, 이것도 ros2_control 하드웨어 인터페이스로 동작합니다. 화낙 문서 기준으로 R-30iB Plus·R-50iA 계열 컨트롤러에 J519 Stream Motion과 R912 Remote Motion 옵션이 필요하고, Humble에서는 `humble` 브랜치를 씁니다. 도입 전에 최신 문서로 다시 확인하세요.

로봇 없이 시험할 때는 **mock** 인터페이스를 씁니다. 로봇 없이 "명령받은 대로 움직였다"고 대답만 하는 가짜 하드웨어예요. ROBOGUIDE나 URSim처럼, 로봇이 도착하기 전에 셀 전체 소프트웨어를 먼저 실행해 볼 수 있습니다. 실물로 넘어갈 때 소프트웨어 쪽은 하드웨어 인터페이스 설정만 바꾸면 됩니다. 다만 실물의 첫 동작은 느린 속도로, 위험성 평가를 마친 셀 안에서 시작해야 합니다.

컨트롤러를 바꾸면 동작 방식도 바뀝니다. 궤적을 따라가는 컨트롤러 대신 정해진 힘으로 누르는 힘 제어용 컨트롤러로 전환하는 식이에요. 로봇이 그런 기능을 지원할 때 이야기지만요.

## 로봇이 움직이기 전에 실수를 잡는 RViz

지금까지 나온 걸 한 화면에 모아 보여 주는 게 **RViz**입니다.

![RViz는 소프트웨어가 믿고 있는 세상을 보여 준다](../assets/diagrams/r2p2-rviz.svg)

그림 왼쪽처럼 보고 싶은 항목을 켜고 끄는 방식입니다. 그중 모션 플래닝 패널(3부)에서는 목표를 마우스로 끌어다 놓고, 계획된 경로를 미리 본 뒤 실행 버튼을 누를 수 있습니다.

RViz는 **데이터를 보여 주기만** 합니다. 화면에서 카메라 좌표계가 반대쪽을 보고 있거나, 부품이 테이블 속에 박혀 있거나, 경로가 지그에 바짝 붙어 지나간다면 로봇이 아니라 데이터가 틀린 겁니다. 로봇이 움직이기 전에 여기서 잡으면 됩니다.

화면이 비었을 때 확인할 곳은 그림에 적어 두었습니다(Fixed Frame은 모든 것을 그리는 기준 좌표계예요). 헷갈리기 쉬운 건 RViz가 시뮬레이터가 아니라는 점입니다. 물리 현상이나 가상의 카메라까지 흉내 내려면 Isaac Sim 같은 시뮬레이터가 따로 필요합니다.

## 정리

| 개념 | 하는 일 | 펜던트로 치면 |
|---|---|---|
| **URDF** | 링크·조인트의 사슬, 관절 범위, 3D 모양 | 컨트롤러에 내장된 로봇 모델, 관절 범위 |
| **xacro** | 재사용할 수 있게 한 URDF, 여러 조각을 조립 | (없음) |
| **robot_state_publisher** | 설계도 + 관절 각도 → 모든 링크 위치를 `/tf`로 | 현재 위치 화면의 계산 |
| **TF2 / TF 트리** | 좌표계를 나무로 연결, 아무 두 좌표계 사이를 계산 | UFRAME·UTOOL |
| **ros2_control** | 공통 컨트롤러 + 로봇별 하드웨어 인터페이스 | 모션 엔진 + 외부 모션 명령 창구 |
| **mock** | 로봇 없이 시험하는 가짜 하드웨어 | ROBOGUIDE, URSim |
| **RViz** | 로봇·좌표계·센서·계획을 3D로 표시 | 펜던트 3D 화면 |

1부의 노드 그래프에 로봇을 연결했으니, [다음 편](moveit2-goals-not-points.md)에서는 드디어 로봇을 목표로 보냅니다. 점을 하나하나 가르치는 대신 목표만 주면 경로를 계산하는 MoveIt 2예요. 화낙의 CONFIG, 간섭 영역, J·L 이동이 거기서 어떤 모습이 되는지 봅니다.

### 출처와 표기

URDF·xacro·robot_state_publisher·TF2·ros2_control·RViz의 동작은 ROS 2 Humble 공식 문서와 ros2_control 문서를, UR 드라이버의 하드웨어 인터페이스(RTDE, External Control, 명령 주기)는 Universal Robots ROS 2 드라이버 문서를, 화낙 드라이버와 요구 사양은 FANUC Corporation이 공개한 `fanuc_driver` 저장소와 문서를 근거로 했습니다. 코드와 터미널 출력은 설명용 예시이며 숫자는 실제 셀 값이 아닙니다. ROS는 Open Source Robotics Foundation(Open Robotics)의, MoveIt은 PickNik Inc.의, FANUC·ROBOGUIDE는 FANUC Corporation의, Universal Robots·UR·URSim·URCaps는 Universal Robots A/S(Teradyne 계열)의, NVIDIA·Isaac Sim·Isaac ROS·cuMotion은 NVIDIA Corporation의 상표이며, 지칭 목적으로만 사용했습니다.

### 용어 설명

- *URDF (Unified Robot Description Format)*: 로봇을 링크와 조인트의 사슬로 적은 설계도 파일
- *링크 · 조인트*: 로봇의 단단한 부분 · 두 링크를 연결하는 관절
- *xacro*: 반복되는 부분을 재사용할 수 있게 만든 URDF 작성 형식
- *robot_state_publisher*: 설계도와 관절 각도로 모든 링크의 위치를 계산해 `/tf`로 내보내는 노드
- *TF2 · TF 트리*: 좌표계 사이의 관계를 관리하는 ROS 라이브러리 · 좌표계들이 나무 모양으로 연결된 구조
- *base_link · tool0*: 관례적으로 쓰는 로봇 베이스 좌표계 · 플랜지 좌표계 이름
- *핸드-아이 캘리브레이션*: 카메라가 툴(또는 셀) 어디에 달렸는지 정밀하게 재는 일
- *쿼터니언(quaternion)*: 방향을 숫자 네 개로 적는 방식. W·P·R 대신 쓴다
- *타임스탬프*: 메시지마다 붙는, 데이터가 만들어진 시각
- *광학 좌표계(optical frame)*: z축이 렌즈 밖으로 뻗도록 잡은 카메라 좌표계
- *ros2_control*: 컨트롤러(공통)와 하드웨어 인터페이스(로봇별)로 모터 제어를 나눈 틀
- *하드웨어 인터페이스*: 공통 명령을 특정 로봇의 통신으로 바꾸는 부분. "ROS 2 드라이버"의 실체
- *mock 하드웨어*: 로봇 없이 명령받은 대로 움직였다고 대답하는 가짜 하드웨어
- *RTDE*: UR 컨트롤러와 실시간으로 데이터를 주고받는 통로
- *RViz*: ROS의 3D 표시 도구. Fixed Frame은 모든 것을 그리는 기준 좌표계
